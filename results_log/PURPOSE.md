# 이 로그의 목적과 독자

`CONVENTION.md`가 **어떻게** 쓸지를 정한다면, 이 문서는 **무엇을 위해** 쓸지를 정한다.
새 로그를 쓰기 전에 이 문서를 먼저 본다.

규약 자체는 옆 저장소 `../CANConv/results_log` 와 동일하다. 두 저장소의 결과를
같은 형식으로 놓고 비교할 수 있어야 하기 때문이다.

## 독자

**pansharpening을 처음 접하고 개념이 아직 잡히지 않은 상태에서 모델을 돌려본 사람.**
이 로그를 원자료로 삼아 **따로 보고서를 작성한다.**

따라서 로그는 그 자체가 보고서일 필요는 없지만, **보고서를 쓸 때 바로 꺼내 쓸 수 있는
형태**여야 한다. 전제 지식을 요구하는 서술은 피하고, 약어와 지표는 처음 나올 때 한 줄로
풀어 쓴다.

## 판단하려는 것

1. **이 기술의 결과물을 직접 눈으로 확인**한다.
2. **실전에 활용 가능한지** 따진다.
3. **CANConv(CVPR 2024) 대비 무엇이 나아졌는지** 같은 데이터·같은 평가로 확인한다.

3번이 이 저장소의 존재 이유다. PanCollection 데이터와 DLPan-Toolbox 평가를
`../CANConv` 와 공유하므로, 두 로그의 수치는 직접 비교 가능해야 한다.

## 이 저장소에만 있는 전제 — 배포 코드와 논문이 어긋난다

PAN-Crafter 배포 코드에는 논문과 다르게 동작하는 지점이 둘 있다
([../KNOWN_ISSUES.md](../KNOWN_ISSUES.md) A-1, A-2). 그래서 이 저장소의 실험은
**baseline(배포본 그대로) 과 fixed(논문대로) 를 쌍으로** 돌린다.

로그에 수치를 적을 때는 **어느 쪽 실행인지 반드시 명시한다.** 이것을 빠뜨리면
"논문 재현에 실패했다" 와 "배포 코드에 버그가 있다" 를 구분할 수 없게 된다.

## 그래서 로그에 반드시 담아야 할 것

목적이 "현실적 판단"이므로 다음이 우선순위가 높다.

| 항목 | 왜 필요한가 |
|---|---|
| **결과물 사진** | 수치보다 먼저 온다. 입력과 출력을 나란히, 확대해서 보여준다 |
| **효과의 크기** | "얼마나 좋아지는가"를 아무것도 안 한 기준선과 비교해 제시한다 |
| **baseline / fixed 구분** | 어느 코드로 낸 수치인지. 이 저장소에서는 필수다 |
| **평가 주체** | 파이썬 로그값인지 DLPan-Toolbox(MATLAB) 값인지. 둘은 다르다 |
| **리소스** | GPU 종류·VRAM 실측·RAM·디스크 |
| **시간** | 학습 시간, 추론 시간. 반복 실험 비용을 가늠할 수 있게 |
| **데이터셋 구조와 요구사항** | 무엇이 있어야 이 기술을 쓸 수 있는지. 우리 데이터에 적용하려면 무엇이 더 필요한지 |
| **활용 가능성과 걸림돌** | 어디까지 믿을 수 있고 어디서 막히는지 |

## 담되 무게를 낮출 것

구현 세부(코드 버그, 이식 과정, 최적화)는 **재현에 필요한 만큼만** 남기고 본문 흐름에서
빼거나 각주·별도 절로 내린다. 독자가 판단하려는 것은 "이 기술을 쓸 것인가"이지
"이 코드를 어떻게 고쳤는가"가 아니다. 상세는 [../KNOWN_ISSUES.md](../KNOWN_ISSUES.md) 에 있으므로
본문에서는 링크로 넘긴다.

다만 **수치의 신뢰도에 영향을 주는 것은 반드시 본문에 남긴다.** A-1/A-2 는 모델 동작
자체를 바꾸므로 구현 세부가 아니라 판단의 근거다.

## 유지되는 원칙

`CONVENTION.md`의 규칙은 그대로 적용된다. 특히:

- 수치의 신뢰도를 명시한다. 기준선을 함께 적는다.
- 배제한 가설을 남긴다.
- 그림은 같은 배율·같은 stretch로 그리고 라벨을 넣는다.
- 문서는 그 시점의 스냅샷이므로 나중에 고치지 않고 새 문서에서 갱신한다.
