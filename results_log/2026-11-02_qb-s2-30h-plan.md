# s2 QB 추가 실험안 — s1 속도 기준 약 34–36시간

사용자 요청: QB는 신규 s2에서 진행하고 s1/s3는 ablation에 사용한다. s1 실측 속도로
약 30시간 규모를 설계하되 30시간에 맞추기 위해 필요한 case를 빼거나 학습을 자르지 않는다.
이 문서는 작성 당시의 **case 설계안**이다. 후속으로 실행 코드와 검증을 완료했다.
현재 실행 방법은 [s2 인계 README](../panda_qb_s2/README.md), 검증 범위는
[구현 기록](2026-11-02_qb-s2-implementation-and-handoff.md)을 따른다.
아래의 미구현 상태 설명과 proposal JSON은 설계 시점의 기록이다. s2 실제 학습은 아직 시작하지 않았다.

실험별 설정은 [JSON](assets/2026-11-02_qb-s2-30h-plan/cases.json),
12개 작업의 실행 순서는 [CSV](assets/2026-11-02_qb-s2-30h-plan/cases.csv),
실측 시간과 기준 코드 검증은 [생성 코드](assets/2026-11-02_qb-s2-30h-plan/build_plan.py)에 있다.
JSON 상태는 `PROPOSAL_NOT_REGISTERED_OR_EXECUTABLE`이며 현재 실행기의 입력 파일이 아니다.

**목적과 근거**

[최신 분석](2026-11-02_qb-a4-results-and-s2-direction.md)에서 A4/E.03은 s1의 RRE50을
.235295→.209725로 낮췄지만 Student 고정30K 평균 HQNR을 .941471→.922587로 악화시켰다.
반면 s3에서는 대표 HQNR을 유지하며 평균 ERGAS가 3.524165→3.516861로 개선됐다.
따라서 Student 손잡이를 바꾸기 전에 같은 s2 환경에서 Stage 1 seed와 계수 효과를 나누어 본다.
기존 A2 기반 최저 적격 ERGAS는 .945384/3.509656이며 QB 목표는 아직 미달이다.

Stage 1 seed 두 개는 역사적 s1/s3 seed를 그대로 사용한다.
이는 seed 번호를 재사용한다는 뜻이며 **weights를 가져오는 것이 아니다**.
모든 Aligner·Teacher·Student를 s2에서 처음부터 학습한다.

- D101 = 261016101: 기존 s1 Stage 1 seed.
- D301 = 261016301: 기존 s3 Stage 1 seed.
- 모든 Student = 261018101: 동일 초기화·샘플 순서·augmentation stream으로 비교.

같은 계수의 D101/D301 차이는 동일 s2 환경에서 Stage 1 seed 의존성을 보여준다.
동일 D101 또는 D301의 A2/A4 차이는 초기화·데이터 순서를 맞춘 계수 비교다.
과거 s1/s3 결과와 함께 보면 서버 환경과 seed가 얽혀 있던 현상을 더 잘 해석할 수 있다.
같은 seed여도 서로 다른 GPU에서 bitwise 동일 결과가 보장되는 것은 아니다.
새 비교의 핵심은 s2 내부에서 코드·데이터·실행 환경과 Student seed를 맞추는 것이다.

**등록할 순서: 6개 완결 case, Stage 1 6회 + Student 6회**

| 순서 | case | λ_abs | λ_ε | Stage 1 seed | Stage 1 → Student | 검증 질문 |
|---:|---|---:|---:|---|---|---|
| 1 | QB6_A200_E030_D101 | 2 | .03 | D101 | 50K → 30K | 기존 s1 A2 기준 재현 |
| 2 | QB6_A400_E030_D101 | 4 | .03 | D101 | 50K → 30K | s1에서의 A4 HQNR 손실 재현 여부 |
| 3 | QB6_A200_E030_D301 | 2 | .03 | D301 | 50K → 30K | 두 번째 seed의 A2 기준 |
| 4 | QB6_A400_E030_D301 | 4 | .03 | D301 | 50K → 30K | s3에서의 A4 특성이 같은 서버에서도 나타나는가 |
| 5 | QB6_A300_E030_D101 | 3 | .03 | D101 | 50K → 30K | A2/A4 사이에서 RR·FR 균형을 찾을 수 있는가 |
| 6 | QB6_A400_E060_D101 | 4 | .06 | D101 | 50K → 30K | A4에서 ε 계수만 올렸을 때 HQNR 손실이 줄어드는가 |

각 case는 Stage 1 완료·validation donor 선택 → calibration → 해당 Student 순서로 끝낸다.
첫 완결 case 결과는 s1 속도 기준 약 5.5시간 뒤에 나온다. 중간 case의 결과로 뒤 case를
자동 취소하거나 donor를 교체하지 않는다. 사용자 검토 후 변경할 경우 별도 revision으로 기록한다.

A4/E.06의 ε/abs 계수비는 .015로 A2/E.03과 같고, A4/E.03의 .0075보다 크다.
이는 계수 균형에 관한 가설 검증이며 실제 loss/gradient 비까지 같다는 뜻은 아니다.
선택된 RR validation epsilon 오차만으로 기존 HQNR 차이가 설명된 것도 아니므로,
E.06의 개선을 전제로 설계하지 않는다.

이번 묶음은 **Stage 1 seed 차이를 보는 1차 비교**다. Student seed는 하나이므로
Stage 2 seed까지 포함한 재현성을 확정할 수 없다. 동일 donor의 Student R2/R3와
새 계수 A3/E.03·A4/E.06의 두 번째 Stage 1 seed는 결과 검토 후 후속으로 둔다.

**공통 방법·학습 설정**

| 항목 | Stage 1 | Stage 2 |
|---|---|---|
| 학습 길이 | 50K | 30K |
| 최고 LR | Aligner 1e-5 / Teacher 1e-4 | Student 1e-4 |
| 스케줄 | warmup100 → 기존 cosine → 0 | warmup100 → 기존 cosine → 0 |
| batch | 48 = micro12 × accumulation4 | 동일 |
| optimizer | 기존 FP32 AdamW, WD .01, betas .9/.999, eps 1e-8 | 동일 |
| 네트워크 | 기존 Aligner·Teacher W112/D123 | W112/D123, DIFF/UBIL |
| 손실 | L_rec + λ_abs L_abs + λ_ε L_ε | 기존 GT Hard, α=.25/γ=.5/β=0 |
| PAN warp | 기존 Lanczos-4 reflection | 동일 |
| Aligner 사용 | 기존 공동 학습 | 해당 donor의 frozen Aligner, scale=1 |

ε 주입은 기존 RR PAN 좌표 반경3px의 uniform-area disk를 유지한다.
이 값은 합성 주입 범위이며 native 예측 shift를 3px로 자르는 clamp를 추가하지 않는다.

Student 입력은 `[corrected PAN, corrected PAN − original PAN, Ilrms]`의 6채널,
출력은 QB 4밴드다. Stage 1·2 구조 참조는 RGB 평균(2,1,0)이고 Aligner의 MS 입력은
등록된 PAN 크기 Stored LMS의 4밴드 전부다. 복원 base는 등록된 LRMS의 interp23이다.
QB train/val의 original Stored LMS override와 msfix LRMS 경로를 현재 방식대로 유지한다.

기존 학습 augmentation과 RNG 파생 규칙을 그대로 사용한다. 회전 일관성 loss·TTA·SWA·
밴드 가중 loss를 추가하지 않는다. batch, LR, width, Hard 계수는 이번 비교의 변수가 아니다.

**s1 실측 예산**

완료된 QB_RRE의 `run_state.json` 시작·종료 시각을 사용했다.
Sheet에서 선택 checkpoint까지만 계산되는 Wall(h)는 전체 run 예산으로 쓰지 않는다.

| 항목 | 1회 | 횟수 | 합계 |
|---|---:|---:|---:|
| Stage 1 50K | 3.027h | 6 | 18.165h |
| Student 30K | 평균 2.448h | 6 | 14.683h |
| 완료 run 합계 | | 12 | **약 32.85h** |
| calibration·선택·게시·시작 검사 및 변동 여유 | | | 약 1–3h |
| 계획 시간 | | | **약 34–36h** |

새 서버의 환경 설치·데이터 전달 시간은 별도다. 30시간 시점에 진행 중인 run을 끊거나
뒤 case를 완료 처리하지 않는다. 단, 아래 기존 조기 중단 또는 실제 실패는 유지한다.

**선택·실패·Sheet·weights**

- Stage 1은 full50K 후 validation RRE50 → RRE90 → ValERGAS → 이른 step으로 선택한다.
  Teacher HQNR 또는 test로 donor를 선택하지 않는다. 새 RRE 절대 문턱을 두지 않는다.
- Student는 공식 8K·9K·10K HQNR이 **모두 .90 미만**일 때만 기존 중단 규칙을 적용한다.
  Teacher에는 이 규칙을 적용하지 않는다.
- Stage 1이 실패하면 해당 Student만 의존 보류하고 나머지 독립 case는 진행한다.
  부분 학습 donor를 사용하거나 shift clipping·loss 변경으로 실패를 숨기지 않는다.
- 공식 목표는 동일 checkpoint의 **HQNR≥.9315 AND ERGAS≤3.5**다.
  평균값, 다른 checkpoint의 HQNR/ERGAS 조합, 진단용 보정 수치는 통과 근거가 아니다.
- `QB-ablations`에 server=`s2`로 게시한다. 목표 동시 통과 전부와 run별 대표 한 개
  (HQNR 충족 후보 중 최소 ERGAS, 없으면 최고 HQNR)를 유지하고 중복은 합친다.
- Approach에는 Stage 1 계수·seed와 Student seed를 함께 표시한다.
  예: `S1 A4/E.06 D101 | S2 R1 C30 LR1e-4 | full-u DIFF/UBIL | α.25 γ.5 β0`.
- 모든 1K 공식 평가 checkpoint와 완전 재개 상태를 저장한다. 목표 통과 여부와 무관하다.
  현 파일 크기를 적용하면 6×50 + 6×30 = 480개 평가 checkpoint의 weights는 약 17GiB이며
  초기 checkpoint·로그·calibration·준비 파일 저장 공간은 추가로 필요하다.
- case별 대표 결과와 고정30K를 함께 비교한다. Stage 1 seed와 Student seed를 분리 표기한다.

**구버전 s2에 전달할 코드의 구현·커밋 조건**

현재 기준 commit은 `ae8e7545f5fb210a6b7878ff4fecc6d818a64391`이다.
현 QB 실행이 추적하는 463개 코드·설정 파일은 모두 Git tracked이고 HEAD와 일치한다.
이 [기준 파일 목록](assets/2026-11-02_qb-s2-30h-plan/reference_code_pin.json)은
기존 QB 구현의 비교 기준이며, 아직 없는 s2 실행 패키지의 검증 완료 기록은 아니다.

현재 실행기는 `--server s1/s3`만 받으며 기존 SENSOR5 컨테이너에서 환경을 상속한다.
따라서 **이전 commit을 pull하고 server 문자열만 s2로 바꾸는 것으로 실행할 수 없다.**
새 s2 구현에서는 다음을 함께 처리해야 한다.

1. 새 campaign/output/게시 namespace와 s2 서버 식별, 위 12개 job과 donor별 두 seed 식별을
   구현한다. 같은 계수의 D101/D301 donor와 calibration cache가 서로 덮어써지지 않아야 한다.
2. 과거 s1/s3 donor·work_dir·컨테이너·큐 완료를 요구하지 않는 새 시작 경로를 만든다.
   실행 후 WV3로 자동 연결하지 않는다. 종료 뒤 해당 s2 QB 큐를 끝낸다.
3. 최신 commit 전체를 새 checkout에 받고 구현·config·launcher·publishing·tests·인계 문서를
   함께 커밋한다. 일부 파일만 복사하거나 과거 패키지 위에 새 config만 덧붙이지 않는다.
   s2 로컬 미커밋 작업은 보존한다. credential·데이터·weights를 Git에 넣지 않는다.
4. clean checkout에서 필요한 Python 파일·config가 빠짐없이 포함됐는지 확인한다.
   실제 Stage 1/Student loss·gradient가 기준 구현과 일치하는지, 완전 재개가 되는지,
   독립 donor 식별과 실패 처리 및 s2 Sheet 게시가 맞는지 검증한다.
5. s2에서 등록 catalog·H5 내용 SHA·original LMS override·split 수·평가 구현을 확인한다.
   기준은 train17139 / val1905 / RR20 / FR20, QB DN peak2047이다.
   오래된 msfix/원본 파일이나 다른 split로 자동 대체하지 않는다.
6. 컨테이너 이미지 digest와 Python/PyTorch/CUDA/NumPy·정밀도 설정을 기록한다.
   s1 기준은 PyTorch2.4.0/CUDA11.8/NumPy1.26.4/FP32, AMP·TF32·cuDNN benchmark off다.
   같은 환경을 사용하고 실제 데이터 update·save/resume·평가의 사전 검사를 거친다.

위 항목은 다음 실행 코드 구현의 완료 조건이다. **현재는 설계 파일만 작성한 상태이며,
s2용 실행 코드 구현·검증·commit 완료를 의미하지 않는다.**
